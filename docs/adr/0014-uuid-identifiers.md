# ADR-0014: Use random UUIDs as public identifiers

- **Status:** Accepted
- **Date:** 2026-10-12
- **Deciders:** Project owner
- **Related:** [contracts/openapi.yaml](../../contracts/openapi.yaml)

## Context

Sequential ids make enumeration trivial and leak volume (how many claims
exist). Ownership checks are the real defense (ADR-0004), but ids shouldn't help
an attacker.

## Decision

- All entity ids are random UUIDs (v4), generated by the application
  (`UUID.randomUUID()`), stored as PostgreSQL `uuid`.
- Business identifiers that already exist (`policyNumber`, `taxId`) are unique
  columns, not primary keys.
- Seed data uses fixed, readable UUIDs (see `specs/fixtures.md`) so tests and
  scripts are deterministic. They exist only in the `local` profile seed.
- Malformed ids in the path → `400`, before any lookup.

## Consequences

- Ids are not guessable. Index locality is worse than sequential keys, which
  is negligible at this scale.

## Alternatives considered

| Option | Why not |
|---|---|
| `bigserial` | Enumerable |
| UUID v7 | Time-ordered (better indexes) but leaks creation time; v4 is fine at this scale |
